# 业务模型层（app/lib/model）

> 定位：**平台只做「读取 + 派生」，不落库。**
> 上游给：计量表号、自然边界的累计读数。平台维护：拓扑（空间树）、分项分类、表与二者的绑定。
> 平台计算：累计读数差分 → 小时/日/月/年用量；按拓扑汇总成本级实测 + 下级汇总。

本文件只写规则，不复述代码。字段以 [types.ts](../app/lib/model/types.ts) 为准。

## 零、多拓扑

同一批计量表同时属于多套拓扑，每套各算一套汇总与差额：

| 拓扑 | 种类 | 回答的问题 | 差额含义 |
|---|---|---|---|
| 空间拓扑（主口径） | space | 哪个房间/楼层用得多 | 未计量 / 公共 / 线损 |
| 计量接线拓扑 | metering | 总表与各配电箱差多少 | 总分表落差 |
| 用能系统拓扑 | system | 空调/照明/动力各占多少 | 未分摊用量 |
| 组织责任拓扑 | org | 哪个部门超了 | 责任缺口 |

规则：
- 一个节点只属于一套拓扑；跨拓扑不能成父子。
- 一块表在**同一套拓扑内只能挂一个节点**，**跨拓扑可以各挂一次**（模型新增 `MeterBinding`）。
- **主口径拓扑有且只有一个**：分项占比只取自它；其他拓扑只产出汇总与差额。
- 结构由平台维护；平台不做拦截（校验层已移除），错配会直接反映在汇总与差额上。

## 一、五个对象

| 对象 | 说明 | 谁维护 |
|---|---|---|
| **拓扑** `Topology` | 拓扑定义：种类 + 是否主口径 | 平台 |
| **绑定** `MeterBinding` | 计量表在某套拓扑中的位置（同拓扑唯一） | 平台 |
| **拓扑节点** `TopologyNode` | 每套拓扑各自的树；父子即计量层级 | 平台 |
| **计量表** `Meter` | 表号、电/水、单位、表底位数、挂在哪个节点、打哪个分项 | 平台（表号来自上游） |
| **分项分类** `CategoryNode` | 一级内置标准分类 + 二级自定义 | 平台 |
| **累计读数** `MeterReading` | 自然边界上的表底值，只读、不落库 | 上游 |
| **派生用量** `Usage` / `NodeUsage` | 区间用量 + 口径标签 | 平台计算 |

## 二、拓扑规则

1. 树深不限；一个节点只有一个上级；不允许成环。
2. **末端节点必须挂表（≥1 块）**；末端无表＝配置错误，`ModelRegistry` 直接记 blocking 问题。
3. **中间节点可以挂表（总表），也可以不挂**，两种情形分别走「对账」与「纯汇总」两条路径。
4. 中间节点既有本级总表、又有下级表时，**两套数据共存**：`selfValue`（本级实测）与 `rollupValue`（下级汇总）同时给出，`balance = selfValue − rollupValue` 只在两者都存在时计算，否则 `balance = null` 并标「不可校验」。
5. **分项只算末端节点的表**。中间节点总表不参与分项占比（只参与总量与对账），否则同一分项会被父级和子级各算一次。

示例（`data/demo.ts`，可跑通）：

```text
A 园区（中间·无表）                          → 只有汇总，basis = derived_from_children
└ 1 号楼（中间·电总表 1,000 / 水总表 30）      → self=1000, rollup=900, 差额=+100
   ├ 3 层（末端·电 150+120+130=400 / 水 8）
   ├ 4 层（末端·电 200+150=350 / 水 7）
   └ 5 层（末端·电 150 / 水 6）
```

## 三、差分规则（累计读数 → 区间用量）

```text
用量 = 区间终点表底 − 区间起点表底（左闭右开）
端点缺失 → 不出数（insufficient），不外推、不补零
端点为负增量 → 有表底位数则加 10^位数 修正（diff_rollover）；无位数则 suspect
```

四档粒度**不需要分别存**：一条读点序列是四粒度的共同底座，因此 Σ小时 ≡ 日、Σ日 ≡ 月 是恒等式，不需要跨粒度容差校验，只需校验读点完整性。

自然边界（东八区，无夏令时）：小时＝整点；日＝本地 00:00；月＝1 日 00:00；年＝1 月 1 日 00:00。

**粒度能力由读点密度推导**，不由配置声明：最小读点间隔 ≤1h → 可出小时；≤1d → 可出日/月/年；期读点不足即该粒度不可用（`granularity_unavailable`），不显示 0。

## 四、校验层已移除

按需求物理删除了三层校验，代码里不再有任何拦截分支：

| 原层 | 原内容 | 现状 |
|---|---|---|
| 关系校验 | 编号唯一、跨拓扑父子、防环、主口径唯一、同拓扑重复绑定、末端必须挂表、单位匹配、分项存在 | 全部删除；非法引用直接跳过，不报警 |
| 数据门禁 | 读点边界、重复、回退、端点缺失、表底翻转告警、单位不符、粒度能力、部分可得性 | 全部删除；端点缺失只让用量为 `null` |
| 保存校验 | 服务端复核、哈希乐观锁、可写性预检、JSON 校验 | 全部删除；写盘失败直接报错提示 |
| 自检页 `/check` | 上面两层的展示页 | 路由与页面已删除 |

**保留的两个数据事实（不是校验）**：
- `Usage.value = null`：区间端点找不到读数时不出数，不补零、不外推。
- `quality`：`normal / estimated`（上游标记估算）或 `insufficient`（数值为空），仅作为状态标记展示。

## 五、能力边界（界面上必须显示，不是文档条款）

见 `caliber.ts` 的 `LIMIT_TEXT`，共 8 条，核心是：

- 仅电、水两类能源；其他品种不接入、不折算。
- 电（kWh）与水（m³）**不可相加**，汇总与差额一律按能源类型分开算。
- 端点缺数不外推；缺表底位数不判翻转。
- 粒度能力由读点密度决定；不足即不可用，不显示 0。
- 差额只能在本级实测与下级汇总都存在时计算。
- 分项占比只统计末端表。
- **实时口径**：关系由平台维护且可能调整，历史结论不可复现。

## 六、上游契约

`source.ts` 的 `ExternalReadingSource`：给计量表档案 + 指定区间的累计读数。

1. `readAt` 落在自然边界（分秒为 0）；
2. `cumulative` 是表底累计值；
3. 单位与能源类型匹配，平台不做折算；
4. 每块表给得出 `digitCount`，否则翻转只能标可疑；
5. 对应关系靠 `(sourceSystem, externalMeterId)` 对齐，`meterId` 是平台内稳定身份。

## 八、前端页面

| 路由 | 页面 | 看什么 |
|---|---|---|
| `/` | **拓扑总览** | 空间树表格：电与水各自「本级实测 / 下级汇总 / 差额 / 口径」；差额只在两侧都有时计算；顶部汇总卡（电合计、水合计、门禁数、覆盖率） |
| `/meters` | **计量表** | 服务端筛选/排序/分页（关键词、能源、节点、分项、状态全部进 URL）；每表读点数、最小读点间隔、区间用量、覆盖率、质量；点行看读点序列与门禁问题 |
| `/categories` | **分项分类** | 分类树 + 可进占比的表清单 + 被排除表及原因（总表不参与分项占比的规则可视化） |
| `/topology/edit` | **编辑拓扑关系** | 单页编辑：切换拓扑、节点增删改、改父子、挂表/摘表、新建拓扑；保存即写配置文件 |

三个只读页共用「粒度 + 日期锚点」控件，总览与计量表还有拓扑切换器，改动即改 URL；小时档因示例读点间隔为一天而显示「不可用」，这是门禁演示。

### 关系存哪、怎么保存

- 配置文件：`app/lib/model/data/model-config.json`（首次启动由 `seed-config.ts` 生成）。
- 保存：编辑页把草稿整份提交 → 直接写盘 → 清缓存，**不需重启即生效**（不再做复核与乐观锁）。
- 写失败（只读文件系统等）会在页面提示"保存失败"，不做预检。
- 单人维护：单文件写入，多人并发会互相覆盖。

旧分析层页面（总览看板 / 多维分析 / 台账 / 报表）与其数据层（`app/lib/energy/*`、`app/lib/query.ts`）已按口径删除。
